## 2. По каждому критерию

### 2.1. Критерий 1 — Качество идентификации и маскирования ПДН (0-6) → **4.5**

**Реализовано:**
- Все 17 типов ПД имеют детектор (`src/main/kotlin/com/alfahack/pii/detection/`): 11 regex + 5 словарных.
- CSV-матрица `src/test/resources/masking-cases.csv` покрывает **все 17 категорий** (строки csv-01..csv-32), включая MULTI. Параметризованный тест `MaskingParameterizedTest` проверяет маскирование + roundtrip демаскирования.
- Маска делает текст нечитаемым: `MaskingEngine.maskValue` заменяет все буквы/цифры на `*`, сохраняя разделители.
- Нет пропусков в рамках покрытых форматов: roundtrip-тесты (`LoadRoundtripReproTest`, `RedisIntegrationTest`) проходят.

**Что не хватает / риски:**
- **КРИТИЧНО (риск систематических пропусков):** примеры из ТЗ не проходят checksum и НЕ маскируются:
  - `4276 1234 5678 9012` (номер карты из ТЗ) **не проходит Luhn** → `CardDetector` даёт confidence 0.5 → отбрасывается порогом 0.7. Жюри, подав пример из ТЗ, увидит, что карта не замаскирована.
  - `770123456789` (ИНН из ТЗ) **не проходит контрольную сумму** → `InnDetector` confidence 0.5 → не маскируется.
  - Это зафиксировано в `docs/test-matrix.md` (раздел 0.4, CK-03, CK-10) как осознанное решение, но для жюри это выглядит как пропуск ПД. **Рекомендация:** при наличии позитивного контекста («карта», «ИНН») маскировать даже при невалидном checksum (стратегия «лучше перемаскировать» из архитектуры не доведена до checksum-типов).
- Дата текстом («двенадцатого мая») не распознаётся — только числовые форматы (`DateDetector`).

### 2.2. Критерий 2 — Корректность демаскирования (0-3) → **2.5**

**Реализовано:**
- Демаскирование по spans (`UnmaskingEngine`) — восстановление исходной строки по позициям, надёжно и точно.
- Roundtrip-тесты: `MaskingParameterizedTest` (шаг 2), `RedisIntegrationTest`, `ProcessControllerTest`.
- Демаскирование ограничено по системе: `ProcessService.unmask` проверяет `system.unmaskingEnabled` → 403 при отключении (`SystemNotAllowedException`).

**Что не хватает:**
- **Нет аутентификации систем** — доступ определяется только по заголовку `X-System-Id` (allowlist). Заголовок тривиально подделывается. Критерий требует «доступно только авторизованной/настроенной системе». Для демо-уровня allowlist + флаг `unmaskingEnabled` частично закрывает требование, но API-ключи/mTLS не реализованы.
- **Нет привязки записи к системе** — любой, кто знает `payload_id`, может демаскировать (запись не привязана к системе-владельцу). Рекомендация: хранить `systemId` в `CorrelationRecord` и проверять при демаскировании.

### 2.3. Критерий 3 — Точность отнесения к ПДН и устойчивость к вариациям (0-4) → **2.5**

**Реализовано:**
- **Ловушки:** «поэт Александр Пушкин», «писатель Лев Толстой», «отделение Банка по адресу...» — не маскируются (`ContextRules` + `NameDetector`/`AddressDetector`). Покрыто тестами `NewDetectorsTest` и `negative-cases.csv` (neg-14..18, neg-16).
- **Разделяющие слова:** «серия 4509 номер 123456» — маскируются только цифры (`PassportDetector`). Покрыто csv-02.
- **Регистронезависимость:** email — да (`Pattern.CASE_INSENSITIVE`), покрыто csv-08.

**Что не хватает:**
- **Даты текстом** («двенадцатого мая 1990 года», «12 мая 1990») — НЕ реализовано. Прямое требование критерия 3.3. `DateDetector` распознаёт только числовые форматы.
- **ФИО в верхнем регистре** («ИВАНОВ ИВАН ИВАНОВИЧ») — НЕ маскируется: regex `NameDetector` `[А-ЯЁ][а-яё]+` требует строчные буквы после первой заглавной. Тест FN-03 в матрице ожидает маскирование, но текущий код не сработает. Это пробел регистронезависимости для словарных детекторов.
- **Вариации адреса** — только формат `г. Город, ул. Улица, д. N, кв. N`; индекс, «родился в Москве» не покрыты.

### 2.4. Критерий 4 — Гибкая настройка и расширяемость (0-4) → **3.5**

**Реализовано:**
- **README есть** (обязательное условие, иначе 0) — `README.md` содержит описание, настройки, инструкцию для жюри.
- **Настройка систем-потребителей:** `pii.systems` в `application.yml` — `enabled`, `masking-types`, `unmasking-enabled`, `mask-format`. `SystemRegistry.resolve`/`filterTypes`.
- **Настройка типов ПД и факта маскирования по системе:** `masking-types` фильтрует типы.
- **Наличие/отсутствие демаскирования по системе:** `unmasking-enabled`.
- **Расширение без переписывания ядра:** новый тип = `Detector` + `PiiType` + правило в конфиге. `DetectionEngine` автоматически подхватывает бины.

**Что не хватает:**
- `mask-format: SYNTHETIC` — заглушка (в `MaskingEngine.maskValue` обрабатывается как STAR). Либо реализовать, либо убрать из документации.
- Перезагрузка конфигурации без рестарта (`@RefreshScope`/Spring Cloud Config) — упомянута в `architecture.md`, но не реализована.
- `docs/README.md` и `docs/test-matrix.md` устарели (см. раздел 4) — могут запутать жюри при проверке настроек.

### 2.5. Критерий 5 — Производительность и SLA (0-4) → **2.5**

**Реализовано:**
- `load_test.py` — нагрузочный тест (маскирование → демаскирование, latency p50/p95/p99, RPS, roundtrip).
- README заявляет: RPS 1210, latency p50 0.028с, p95 0.106с, p99 0.131с, 100% успешных.
- Архитектура: виртуальные потоки, скомпилированные regex, Redis + circuit breaker, rate limiting (Bucket4j, лимит 2000).

**Что не хватает:**
- **RPS 2000 не достигнут** (текущий 1210). Целевой уровень RPS 1000 при latency ≤ 0.5с — достигнут; повышенный RPS 2000 — нет.
- **Нет теста на 100 000 токенов.** `maxPayloadSize` = 1 000 000 символов, но нет нагрузочного/функционального теста с текстом на 100 000 токенов. Чанкинг больших текстов (из `architecture.md` 16.6) не реализован — детекция линейная, но на очень больших текстах может деградировать.
- Заявленные цифры производительности не верифицированы в этом ревью (нет запущенного сервиса). Рекомендация: приложить лог/вывод `load_test.py` как артефакт.

### 2.6. Критерий 6 — Безопасность, логирование и метрики (0-3) → **2.5**

**Реализовано:**
- **Логирование типов ПД по запросу:** `ProcessService` логирует `typesSummary` (типы без значений). `LogMasker` маскирует payload_id. Тест `SecurityLogTest` проверяет отсутствие утечек.
- **Метрики Latency/RPS:** `MetricsService` — `pii_latency_seconds` (p50/p95/p99), `pii_requests_total`, `pii_requests_masking_total`, `pii_requests_unmasking_total`, `pii_entities_detected_total`, `pii_rate_limited_total`. Экспорт через `/actuator/prometheus`.
- **Ограничение систем:** allowlist по `X-System-Id` → 403 для неизвестных. Тест `SystemAccessTest`.
- **Нет утечек ключей/ПД в артефактах:** LogMasker, метрики без значений.
- **Обработка ошибок:** `GlobalExceptionHandler` — 400/403/404/429/500/503, понятные сообщения. Тесты `PayloadSizeTest`, `RateLimitTest`, `CircuitBreakerTest`, `EdgeCaseTest`.

**Что не хватает:**
- **Метрика TPS (токенов в секунду)** — упомянута в `architecture.md` (15.1, `pii_tps`), но НЕ реализована в `MetricsService`. Критерий требует Latency/RPS/TPS.
- **Нет явной метрики RPS** (gauge) — RPS выводится из `requests_total`, но отдельного счётчика нет.
- **Нет API-ключей/mTLS** — только заголовок `X-System-Id` (см. критерий 2).

### 2.7. Критерий 7 — Расширенные сценарии (0-3) → **1.5**

| Сценарий | Статус | Балл |
|----------|--------|------|
| Токенизация/детокенизация или синтетика | Частично: `mask-format: TOKEN` (замена на `X`) реализован; `SYNTHETIC` — заглушка | ~0.5 |

| Документы кроме паспорта РФ (загранпаспорт, СНИЛС) | НЕ реализовано | 0 |
| Контекстное маскирование (PIN + карта, настраиваемое правило) | НЕ реализовано | 0 |

**Итого: ~1.5 / 3.** Уверенно показан только «формат маски по системе». Токенизация — частично.

### 2.8. Критерий 8 — Качество демо и презентации (0-3) → **2.5**

**Реализовано (артефакты):**

## 5. План исправлений

## 6. Приоритеты по влиянию на баллы

| Приоритет | Действие | Влияние |
