## 1. Цель и назначение

Сервис выполняет роль **прокси-компонента** между системой-потребителем и LLM. Он обрабатывает запросы, отправляемые в LLM, и ответы, формируемые LLM, выполняя:

1. **Идентификацию** персональных данных (ПД) — определение типа и позиций ПД в тексте.
2. **Маскирование** — замену ПД на маску (токенизация с сохранением длины) перед отправкой в LLM.
3. **Демаскирование** — восстановление исходных ПД в ответе LLM.

**Цель:** качественно и быстро обрабатывать запросы/ответы, выдерживать нагрузку обращений к LLM (RPS 1000+, latency ≤ 1 сек), обеспечивать безопасность ПД (никаких утечек в логи/метрики), быть расширяемым (новые типы ПД и правила без переделки сервиса).

## 2. Термины и сокращения

| Термин | Определение |
|--------|-------------|
| **ПД** | Персональные данные |
| **LLM** | Large Language Model (большая языковая модель) |

| **TPS** | Tokens Per Second (токенов в секунду) |
| **NER** | Named Entity Recognition (распознавание именованных сущностей) |

| 16 | Пин-код карты | 1234 |
| 17 | Имя держателя карты | IVANOV IVAN |

**Дополнительные требования:**
- Механизм определения принадлежности данных именно к ПД (упоминание поэта Александра Пушкина — не ПД; адрес отделения Банка — не ПД).
- Расширяемость списка идентифицируемых ПД.
- Регистронезависимость идентификации.
- Логирование выявленных типов ПД по каждому запросу.
- Учёт вариаций написания: регистр, разные форматы дат (мм.дд.гггг, гггг.дд.мм, текстом), разделяющие слова («серия хххх номер хххххх»).
- Демаскирование с сохранением местоположения знаков.
- Качество идентификации/маскирования/демаскирования ≥ 95%.
- Обработка текста до 100 000 токенов.

### 3.2. Нефункциональные требования

| Требование | Значение |
|------------|----------|
| **Latency** | ≤ 1 сек (ориентир) |
| **RPS** | 1000 (цель 2000) |
| **Таймаут запроса** | 10 сек |
| **Ретраи** | до 2 (итого 3 попытки) |
| **429** | допустим (с Retry-After), но не должен сохраняться |
| **Стоп** | после 5 невалидных запросов подряд (429 не считается) |
| **Безопасность** | никаких утечек ПД в логи/метрики |
| **Масштабируемость** | добавление новых типов ПД и увеличение RPS без потери latency |

### 3.3. Метрика качества (из ответов жюри)

- **Метрика:** нормированное **span-based расстояние Левенштейна** [0..1].
- Маска сравнивается с **оригиналом** (эталонной маски не существует).
- **Лишние маски штрафуются СЛАБЕЕ, чем пропуски** → стратегия: лучше перемаскировать, чем пропустить.
- Полное маскирование строки штрафуется, если избыточно.
- Разделители (точки, дефисы, пробелы внутри значения) можно оставлять.
- Длина маски не критична (метка короче/длиннее оригинала не влияет).
- Служебные слова («серия», «ул.», «года») маскировать не нужно (штраф за избыточность).
- Проверяющая система шлёт запросы **без заголовков** → одна «система по умолчанию».

## 4. Принятые архитектурные решения

| Решение | Выбор | Обоснование |
|---------|-------|-------------|
| **Идентификация** | Гибрид regex + ML/NER (паттерн Analyzer/Recognizer) | Regex — для структурированных типов (паспорт, ИНН, телефон, email, карта), ML — для неструктурированных (ФИО, адреса, места рождения). Паттерн по образцу Microsoft Presidio. ML-часть проектируется позже, бэкенд готов через абстракцию `Detector`. |
| **Хранилище соответствий** | Redis (внешний) | Масштабируется на N инстансов, переживает рестарты, TTL-автозачистка. Клиент Lettuce (асинхронный, поддерживает виртуальные потоки). |
| **Формат маски** | Токенизация с сохранением длины | Замена символов на `*`, сохраняя длину и разделители (`45** ****56`). Лучше всего для span-based метрики, демаскирование тривиально по позициям. |
| **Масштаб этапа** | Полный дизайн-документ | Архитектура без кода. ML-система — отдельный этап. |
| **Повышение точности** | Checksum-валидация + контекстные правила | ИНН (контрольная сумма), карты (Luhn), паспорт (формат+контекст). Контекстные правила отличают ПД от упоминаний (Пушкин ≠ ПД). |
| **Отказоустойчивость** | Circuit breaker + rate limiting | Resilience4j (circuit breaker), Bucket4j (rate limiting → 429). Деградация при недоступности Redis/ML. |
| **Производительность** | Виртуальные потоки | Spring Boot 4 / Spring Framework 7, `spring.threads.virtual.enabled=true`. Тысячи параллельных запросов при малом потреблении памяти. |

### 5.2. Поток обработки запроса

**Маскирование (первый запрос с новым payload_id):**

```
1. Приём запроса {payload, payload_id}
2. Определение системы (по заголовку или «по умолчанию»)
3. Проверка прав системы (включена ли)
4. Идентификация ПД в payload (детекторы: regex + ML)
5. Фильтрация типов ПД по правилам системы
6. Маскирование найденных ПД (токенизация с сохранением длины)
7. Сохранение соответствия в Redis: payload_id → {original, mask, spans}
8. Возврат {result: mask}
```

**Демаскирование (второй запрос с тем же payload_id):**

```
1. Приём запроса {payload, payload_id}
2. Поиск соответствия в Redis по payload_id
3. Если найдено → восстановление исходной строки по spans
4. Возврат {result: original}
5. Если не найдено → 404/ошибка (или повторное маскирование, см. идемпотентность)
```

### 5.3. Ключевые принципы

- **Расширяемость:** новый тип ПД = новый детектор + enum `PiiType` + правило в конфиге. Без переделки сервиса.
- **Стратегия «лучше перемаскировать»:** лишние маски штрафуются слабее пропусков.
- **Идемпотентность:** повторный запрос с тем же payload_id возвращает тот же результат.
- **Безопасность:** ПД не попадают в логи и метрики.

## 7. API-контракт `/process`

### 7.1. Спецификация

```
POST /process
Content-Type: application/json

Запрос:
{
  "payload": "<строка>",
  "payload_id": "<идентификатор>"
}

Ответ (200):
{
  "result": "<строка>"
}
```

### 7.2. Логика

| Шаг | payload_id | payload | Действие | Ответ |
|-----|------------|---------|----------|-------|
| 1 | новый | исходная строка | **маскирование** | маска |
| 2 | тот же | ваша маска | **демаскирование** | исходная строка |

### 7.3. Коды ответов

| Код | Описание |
|-----|----------|
| **200** | Успешная обработка |
| **400** | Некорректный запрос (нет payload/payload_id, payload слишком большой) |
| **403** | Неизвестная/отключённая система, демаскирование запрещено для системы |
| **404** | Соответствие по payload_id не найдено |
| **429** | Too Many Requests (с Retry-After) — допустим под нагрузкой |
| **500** | Внутренняя ошибка сервиса |
| **503** | Redis недоступен (деградация, circuit breaker) |

### 7.4. Идемпотентность

- Повторный запрос с тем же payload_id и тем же payload возвращает **тот же результат**.
- Это критично для ретраев (до 3 попыток).
- Реализация: при маскировании — если запись уже есть и payload совпадает, вернуть сохранённую маску; при демаскировании — вернуть сохранённый оригинал.

## 8. Модуль идентификации ПД

### 8.1. Паттерн: Analyzer / Recognizer (по образцу Microsoft Presidio)

Модуль идентификации построен по проверенному паттерну **Analyzer / Recognizer** (используется в Microsoft Presidio — эталонном open-source решении для PII-детекции). Это обеспечивает:

- **Расширяемость** — новые типы ПД добавляются как новые recognizer'ы без изменения ядра.
- **Комбинирование стратегий** — NER + regex + rule-based + checksum-валидация.
- **Прозрачность** — можно трассировать, почему сущность была помечена (важно для аудита и отладки).

```
┌──────────────────────────────────────────────────────────────┐
│  DetectionEngine (Analyzer)                                  │
│  • оркестрация recognizer'ов                                 │
│  • объединение результатов                                   │
│  • разрешение пересечений                                    │
│  • применение контекстных правил                             │
│  • пороги уверенности                                        │
└───────┬──────────────────────────────────────────────────────┘
        │  вызывает каждый recognizer
        ▼
┌──────────────────────────────────────────────────────────────┐
│  Recognizer (интерфейс Detector)                             │
│  ┌──────────────┐ ┌──────────────┐ ┌──────────────────────┐  │
│  │ RegexRecognizer│ │ NerRecognizer│ │ DictionaryRecognizer│  │
│  │ (паспорт, ИНН, │ │ (ФИО, адрес, │ │ (имена, города,     │  │
│  │  телефон, карта)│ │  место рожд.)│ │  улицы, гражданство)│  │
│  └──────────────┘ └──────────────┘ └──────────────────────┘  │
└──────────────────────────────────────────────────────────────┘
```

### 8.2. Интерфейс recognizer'а (абстракция)

```kotlin
interface Detector {
    val supportedTypes: Set<PiiType>
    fun detect(text: String): List<DetectedEntity>
}
```

**`DetectedEntity`:**
```kotlin
data class DetectedEntity(
    val type: PiiType,          // тип ПД
    val start: Int,             // начальная позиция (включительно)
    val end: Int,               // конечная позиция (исключительно)
    val confidence: Double,     // уверенность [0..1]
    val source: DetectorSource, // REGEX | ML | DICTIONARY | CONTEXT
    val validated: Boolean      // прошла ли checksum-валидация
)
```

**`PiiType` (enum, 17 категорий):**
```kotlin
enum class PiiType {
    FULL_NAME, DATE_OF_BIRTH, PLACE_OF_BIRTH, PASSPORT_SERIES_NUMBER,
    CITIZENSHIP, PASSPORT_ISSUER, PASSPORT_DEPARTMENT_CODE, PASSPORT_ISSUE_DATE,
    DRIVER_LICENSE, ADDRESS, EMAIL, PHONE, INN, CARD_NUMBER, CVV, PIN, CARD_HOLDER_NAME
}
```

### 8.3. Типы recognizer'ов

| Тип | Категории | Скорость | Точность | Checksum |
|-----|-----------|----------|----------|----------|
| **Regex** | паспорт, ИНН, телефон, email, карта, CVV, ПИН, даты, в/у, код подразделения | высокая | высокая | ИНН, карта (Luhn), паспорт |
| **ML/NER** (позже) | ФИО, адреса, места рождения, гражданство, орган выдачи | средняя | высокая | — |
| **Словари + контекст** | ФИО (имена), города, улицы, гражданство | высокая | средняя | — |

### 8.4. Checksum-валидация (снижение ложных срабатываний)

Критично для качества (метрика штрафует за лишние маски, хоть и слабее пропусков). Для структурированных типов применяется **валидация контрольной суммы**:

| Тип | Валидация |
|-----|-----------|
| **ИНН** | Алгоритм контрольной суммы ИНН (10/12 цифр, весовые коэффициенты) |
| **Номер карты** | Алгоритм **Luhn** |
| **Паспорт** | Формат серии/номера + контекст («паспорт», «серия», «номер») |
| **Телефон** | Формат + код страны/оператора |
| **Email** | Формат + наличие домена |

- Если checksum не прошла → confidence снижается, сущность может быть отброшена (если нет контекста ПД).
- Если checksum прошла → confidence повышается, сущность маскируется.

### 8.5. Контекстные правила (определение принадлежности к ПД)

Ключевое требование ТЗ: «упоминание поэта Александра Пушкина не является ПД, как и адрес отделения Банка». Решается **контекстными правилами**:

- **Позитивный контекст** (усиливает уверенность): «паспорт», «серия», «номер», «дата рождения», «карта», «ИНН», «телефон», «адрес», «прописка», «выдан», «код подразделения».
- **Негативный контекст** (снижает уверенность): «поэт», «писатель», «отделение Банка», «филиал», «улица Пушкина» (топоним, не ФИО).
- **Правило:** ПД маскируется, если есть **однозначная структура** (checksum прошла) ИЛИ **позитивный контекст** ПД.
- ФИО без контекста ПД (паспорт, дата рождения) → НЕ маскируется (это может быть упоминание известной личности).

### 8.6. Двухэтапная идентификация (оптимизация производительности)

Для обработки больших текстов (до 100 000 токенов) применяется **двухэтапная стратегия**:

```
Этап 1: Быстрый regex-скрининг (все regex-детекторы)
  → находит кандидатов (структурированные типы)
  → дешёвый, линейный по длине текста

Этап 2: ML/NER (только при необходимости)
  → для неструктурированных типов (ФИО, адреса)
  → запускается на фрагментах, где regex не дал результата
  → или параллельно для полного покрытия
```

- Для коротких запросов (типичных для проверяющей системы) — только regex (быстро).
- Для больших текстов — regex + ML (полное покрытие).

### 8.7. Регистронезависимость

- Перед детекцией текст нормализуется (lowercase) для regex-детекторов.
- Позиции в оригинале сохраняются через mapping (нормализованный текст ↔ оригинал).
- Regex-паттерны используют `Pattern.CASE_INSENSITIVE | Pattern.UNICODE_CASE`.

### 8.8. Разрешение пересечений

- Если несколько recognizer'ов нашли перекрывающиеся spans:
  - Выбирается более специфичный тип (по приоритету).
  - Или тип с более высокой уверенностью.
  - Или тип, прошедший checksum-валидацию.
- Приоритет типов (от более специфичного к менее): CVV > PIN > CARD_NUMBER > PASSPORT > INN > PHONE > EMAIL > DATE > FULL_NAME > ADDRESS.

### 8.9. Расширяемость

- Новый тип ПД = новый recognizer (реализует `Detector`) + значение в `PiiType` + правило в конфиге системы.
- Регистрация через Spring (recognizer'ы — бины, автоматически подхватываются `DetectionEngine`).
- Конфигурация recognizer'ов из YAML (no-code подход, как в Presidio).

### 8.10. ML-интеграция (готовность)

- Интерфейс `Detector` уже готов для ML-детектора (`NerDetector`).
- ML-детектор будет реализован позже (отдельный этап) и зарегистрирован как бин.
- `DetectionEngine` не меняется — он просто получит ещё один recognizer в списке.
- Для ML-модели предусмотрен отдельный сервис/контейнер (не блокирует основной поток).

## 9. Модуль маскирования

### 9.1. Токенизация с сохранением длины

- Каждый символ ПД заменяется на `*`.
- **Разделители** (точки, дефисы, пробелы, слэши внутри значения) **сохраняются**.
- Пример: `4509 123456` → `45** ****56` (или `**** ******`).

### 9.2. Правила маскирования

| Правило | Описание |
|---------|----------|
| Сохранение длины | длина маски = длина оригинала |
| Сохранение разделителей | точки, дефисы, пробелы внутри значения не маскируются |
| Регистронезависимость | идентификация не зависит от регистра |
| Форматы дат | мм.дд.гггг, гггг.дд.мм, текстом («двенадцатого мая») |
| Разделяющие слова | «серия хххх номер хххххх» — маскируются только цифры, слова «серия»/«номер» — нет |
| Служебные слова | «ул.», «года», «серия» — НЕ маскируются (штраф за избыточность) |

### 9.3. Стратегия «лучше перемаскировать»

- Т.к. лишние маски штрафуются слабее пропусков, при неуверенности детектора (confidence ниже порога) — **маскируем**.
- Но избегаем полного маскирования строки, если это избыточно (штраф).
- **Пороги уверенности** (настраиваемые):
  - `confidence >= 0.9` → маскируем всегда.
  - `0.7 <= confidence < 0.9` → маскируем, если есть позитивный контекст.
  - `confidence < 0.7` → не маскируем (риск ложного срабатывания).

### 9.4. Обработка разных форматов

**Даты (несколько форматов):**
- `дд.мм.гггг`, `мм.дд.гггг`, `гггг.дд.мм`, `гггг-мм-дд`.
- Текстом: «двенадцатого мая 1990 года», «12 мая 1990».
- Маскируются только цифры/значение, слова «года», «мая» — нет.

**Паспорт:**
- «серия 4509 номер 123456» → маскируются только `4509` и `123456`.
- «4509 123456» → маскируются обе группы.

**Телефон:**
- `+7 (900) 123-45-67`, `89001234567`, `8-900-123-45-67`.
- Маскируются цифры, разделители `+`, `(`, `)`, `-`, пробелы сохраняются.

**Карта:**
- `4276 1234 5678 9012` → `42** **** **** 9012` (или полное маскирование).
- CVV `123` → `***`.
- PIN `1234` → `****`.

### 9.5. Результат маскирования

```kotlin
data class MaskingResult(
    val maskedText: String,          // замаскированный текст
    val spans: List<MaskedSpan>      // карта соответствий для демаскирования
)

data class MaskedSpan(
    val type: PiiType,
    val start: Int,                  // позиция в маске
    val end: Int,
    val original: String             // исходное значение (для демаскирования)
)
```

### 9.6. Оптимизация для больших текстов

- Маскирование выполняется за один проход по тексту (линейная сложность).
- Spans сортируются по позиции, применяются последовательно.
- Для текстов > N символов — потоковая обработка по чанкам (с перекрытием границ для детекции).

## 10. Модуль демаскирования

### 10.1. Принцип

- Демаскирование получает **вашу маску без изменений** (из ТЗ: «На демаскирование всегда приходит наша маска без изменений»).
- Восстановление выполняется **по spans** (карте соответствий), сохранённой в Redis при маскировании.

### 10.2. Алгоритм

```
1. Получить CorrelationRecord из Redis по payload_id
2. Для каждого MaskedSpan:
   - найти позиции [start, end) в маске
   - заменить на original
3. Вернуть восстановленную строку
```

### 10.3. Надёжность

- Т.к. маска приходит без изменений, восстановление по позициям **тривиально и надёжно**.
- Если маска отличается от сохранённой (не наш случай по ТЗ) — fallback: повторная идентификация и сопоставление.

## 11. Хранилище соответствий (Redis)

### 11.1. Выбор структуры данных

Рекомендуется **Redis Hash** (или JSON-тип Redis Stack) для атомарного обновления полей:

**Ключ:** `pii:corr:{payload_id}`

**Hash-поля:**
| Поле | Тип | Описание |
|------|-----|----------|
| `original` | string | исходная строка |
| `mask` | string | замаскированная строка |
| `spans` | JSON string | карта соответствий (массив MaskedSpan) |
| `createdAt` | long | timestamp создания |
| `status` | string | `MASKED` / `UNMASKED` |

**Пример (JSON-представление):**
```json
{
  "original": "Клиент Иванов Иван Иванович, паспорт 4509 123456",
  "mask": "Клиент И. И. И., паспорт 45** ****56",
  "spans": [
    {"type": "FULL_NAME", "start": 8, "end": 26, "original": "Иванов Иван Иванович"},
    {"type": "PASSPORT_SERIES_NUMBER", "start": 38, "end": 50, "original": "4509 123456"}
  ],
  "createdAt": 1727000000000,
  "status": "MASKED"
}
```

### 11.2. TTL

- TTL по умолчанию: **24 часа** (настраиваемый).
- Автозачистка Redis по TTL — не нужно ручное удаление.
- TTL продлевается при обращении (опционально).

### 11.3. Идемпотентность (критично для ретраев)

- **Маскирование:** если запись уже существует и `original` совпадает с payload → вернуть сохранённую `mask` (без повторного маскирования). Если `original` отличается → новый payload_id (или ошибка).
- **Демаскирование:** если запись существует → вернуть `original`.
- **Атомарность:** операции `SETNX` / `HSETNX` для защиты от гонок при параллельных ретраях.

### 11.4. Деградация при недоступности Redis

- При недоступности Redis:
  - **Маскирование:** можно вернуть маску без сохранения (с предупреждением), но демаскирование станет невозможным. Либо вернуть 503.
  - **Демаскирование:** вернуть 503 с понятным сообщением.
- Рекомендация: при недоступности Redis возвращать **503** (чтобы не потерять данные для демаскирования).
- **Circuit breaker** (Resilience4j) для защиты от каскадных сбоев.

### 11.5. Клиент Redis

- **Lettuce** (рекомендуется, асинхронный, высокопроизводительный, поддерживает виртуальные потоки).
- Пул соединений, таймауты (короткие, ~500 мс).
- Redis Cluster для масштабирования (при необходимости).

### 11.6. Масштабирование

- Redis Cluster / Sentinel для отказоустойчивости.
- Шардирование по payload_id (hash-слоты).
- Репликация для чтения.

- По заголовку запроса (например, `X-System-Id`).
- Если заголовка нет → **система по умолчанию** (проверяющая система).

### 12.3. Гибкая настройка

- Список систем (вкл/выкл доступа).
- Перечень типов ПД для идентификации/маскирования в зависимости от системы.

- Формат маски в зависимости от системы (STAR/TOKEN/SYNTHETIC — расширяемость).

### 12.4. Краткая инструкция по настройке (≤ 5 предложений)

Добавьте систему с уникальным именем, укажите `enabled: true`, перечислите типы ПД в `maskingTypes` (или `ALL`) и включите/выключите `unmaskingEnabled`. Для запросов без заголовка используется система `default`. Изменения применяются без перезапуска через перезагрузку конфигурации.

## 13. Обработка ошибок и отказоустойчивость

### 13.1. Коды ошибок

| Код | Ситуация | Действие |
|-----|----------|----------|
| **400** | Некорректный запрос (нет payload/payload_id) | вернуть ошибку |
| **403** | Неизвестная/отключённая система | вернуть ошибку |
| **404** | Соответствие по payload_id не найдено | вернуть ошибку |
| **429** | Перегрузка | вернуть 429 с Retry-After |
| **503** | Redis недоступен | вернуть 503 |
| **500** | Внутренняя ошибка | вернуть 500 |

### 13.2. Rate Limiting (429)

- Реализация: **Bucket4j** (рекомендуется) или Resilience4j.
- При превышении лимита → 429 с заголовком `Retry-After`.
- 429 допустим под нагрузкой, но не должен сохраняться (иначе решение не держит нагрузку).
- Лимит настраиваемый (например, 2000 RPS на инстанс).

### 13.3. Идемпотентность (ретраи)

- Эндпоинт безопасен к ретраям (до 3 попыток).
- Повторный запрос с тем же payload_id возвращает тот же результат.
- Атомарные Redis-операции (`SETNX`/`HSETNX`) для защиты от гонок.

### 13.4. Circuit Breaker (Resilience4j)

- **Redis:** при недоступности — circuit breaker открывается, запросы быстро возвращают 503 (без ожидания таймаута).
- **ML-детектор:** при недоступности — fallback на regex-детекторы (частичная деградация).
- Автоматическое восстановление после таймаута.

### 13.5. Деградация

- При недоступности Redis → 503 (не теряем данные для демаскирования).
- При недоступности ML-детектора → fallback на regex-детекторы (частичная деградация).
- Понятные сообщения пользователю.

### 13.6. Таймауты

- Таймаут запроса: 10 сек (по ТЗ).
- Таймауты Redis-операций: короткие (например, 500 мс), чтобы не блокировать поток.
- Таймауты ML-детектора: короткие (например, 1 сек), fallback на regex.

### 13.7. Graceful degradation под нагрузкой

- При перегрузке (высокий RPS) — приоритет на маскирование (критично для безопасности).
- Демаскирование может быть отложено/ограничено при перегрузке.
- Очередь запросов с ограничением размера (защита от переполнения памяти).

## 14. Безопасность

### 14.1. Маскирование логов (критично)

- **Критично:** ПД не должны попадать в логи (требование ТЗ: «не попадают ли исходные защищаемые данные в логи и технические метрики»).
- Реализация: `LogMasker` — фильтр/декоратор логгера, который маскирует ПД в сообщениях.
- **Логирование типов ПД без значений:** «Обнаружены типы: FULL_NAME, PASSPORT_SERIES_NUMBER» (без самих значений).
- **Никогда не логировать:** payload, original, mask, spans (значения).
- **Логировать:** payload_id (хеш), типы ПД, latency, статус, количество найденных сущностей.

### 14.2. Отсутствие ПД в метриках

- Метрики содержат только агрегированные значения (latency, RPS, TPS, количество), без значений ПД.
- Никаких тегов с ПД в Prometheus-метриках.

### 14.3. Шифрование

- **Данные в Redis** могут быть зашифрованы (AES) при необходимости (original, mask, spans).
- **Транспорт:** HTTPS (самоподписанный сертификат допускается, проверка с ssl_verify=false).
- **Ключи шифрования** — в защищённом хранилище (Vault / env).

### 14.4. Минимизация данных

- Хранится только необходимое для демаскирования (original, mask, spans).
- TTL ограничивает время хранения (24 часа).
- Не хранить лишние данные.

### 14.5. Ограниченный список систем

- Только системы из конфигурации имеют доступ.
- Неизвестная система → 403.
- Аутентификация/авторизация систем (API-ключи, заголовки) — опционально.

### 14.6. Защита от атак

- **Ограничение размера payload** — защита от DoS.
- **Rate limiting** — защита от перегрузки.
- **Валидация входных данных** — защита от некорректных запросов.
- **Таймауты** — защита от зависаний.

## 16. Производительность

### 16.1. Виртуальные потоки (ключевое решение)

- **Spring Boot 4 / Spring Framework 7** поддерживает виртуальные потоки (Java 21+).
- `spring.threads.virtual.enabled=true` — включить.
- Виртуальные потоки позволяют держать **тысячи параллельных запросов** при малом потреблении памяти (в отличие от платформенных потоков).
- Это критично для RPS 1000+ при latency < 1 сек.
- **Важно:** виртуальные потоки эффективны для **блокирующих** операций (Redis I/O), т.к. блокировка не занимает платформенный поток.

### 16.2. Асинхронность и неблокирующие операции

- Redis-операции асинхронные (Lettuce, reactive).
- Не блокировать поток на ожидании Redis.
- Использовать `CompletableFuture` / coroutines (Kotlin) для композиции асинхронных операций.

### 16.3. Rate Limiting (429)

- **Bucket4j** (рекомендуется) или **Resilience4j RateLimiter**.
- Лимит: настраиваемый (например, 2000 RPS на инстанс).
- При превышении → 429 с заголовком `Retry-After`.
- 429 допустим под нагрузкой, но не должен сохраняться (иначе решение не держит нагрузку).

### 16.4. Кэширование

- **Скомпилированные regex-паттерны** — компилируются один раз при старте, не на каждый запрос.
- **Словари** (имена, города, улицы) — загружаются в память, обновляются по расписанию.
- **Конфигурация систем** — кэшируется, перезагружается без рестарта.
- **Результаты детекции** — опционально (для повторяющихся payload).

### 16.5. Оптимизация regex

- Предварительная компиляция паттернов (`Pattern.compile` при старте).
- Ограничение backtracking (атомарные группы `(?>...)`, possessive quantifiers `*+`).
- `Pattern.CASE_INSENSITIVE | Pattern.UNICODE_CASE` для регистронезависимости.
- Линейная сложность по длине текста.

### 16.6. Обработка больших текстов (100 000 токенов)

- **Линейная сложность** по длине текста (один проход).
- **Чанкинг:** для текстов > N символов — разбиение на чанки с перекрытием границ (для корректной детекции на стыках).
- **Потоковая обработка** — не держать весь текст в памяти при необходимости.
- **Ограничение размера payload** — защита от DoS (настраиваемый лимит).

### 16.7. Пул соединений Redis

- Настроенный пул соединений (Lettuce).
- Таймауты (короткие, ~500 мс), чтобы не блокировать потоки.
- Мониторинг пула (активные/простаивающие соединения).

### 16.8. Тюнинг Tomcat

- `server.tomcat.threads.max` — при использовании виртуальных потоков не критично (виртуальные потоки не ограничены).
- `server.tomcat.accept-count` — очередь принятых соединений.
- `server.tomcat.max-connections` — максимальное число соединений.
- Keep-alive для повторного использования соединений.

### 16.9. Профилирование и нагрузочное тестирование

- **JMeter / Gatling / k6** для нагрузочного тестирования.
- Целевые метрики: RPS 1000+ (цель 2000), latency p95 < 1 сек.
- Профилирование (JFR, async-profiler) для поиска узких мест.

## 17. Стратегия обеспечения качества (метрика ≥ 95%)

### 17.1. Метрика качества

- **Метрика:** нормированное span-based расстояние Левенштейна [0..1].
- Маска сравнивается с **оригиналом** (эталонной маски нет).
- **Лишние маски штрафуются СЛАБЕЕ, чем пропуски** → стратегия «лучше перемаскировать».

### 17.2. Ключевые факторы качества

| Фактор | Влияние на метрику |
|--------|--------------------|
| **Полнота детекции** | Пропуск ПД → сильный штраф. Нужно минимизировать пропуски. |
| **Точность детекции** | Лишняя маска → слабый штраф. Меньше критично, но влияет. |
| **Сохранение длины** | Маска той же длины → меньшее расстояние Левенштейна. |
| **Сохранение разделителей** | Разделители не маскируются → меньшее расстояние. |
| **Не маскировать служебные слова** | «серия», «ул.», «года» не маскируются → меньше штраф за избыточность. |

### 17.3. Стратегия «лучше перемаскировать»

- При неуверенности (confidence ниже порога) — **маскируем** (пропуск штрафуется сильнее).
- Но избегаем полного маскирования строки (избыточность штрафуется).
- Пороги уверенности настраиваются под эталонный датасет.

### 17.4. Тестирование качества

- **Эталонный датасет** (17 категорий, включая сложные предложения).
- **Оценка:** для каждого элемента — маскирование → сравнение с оригиналом (span-based Левенштейн).
- **Цель:** средняя метрика ≥ 95%.
- **Итеративная настройка:** пороги уверенности, контекстные правила, checksum-валидация.

### 17.5. Инструменты оценки

- Собственный скрипт оценки (Python/Kotlin) для прогона по датасету.
- Отчёт по каждой категории (precision/recall/F1).
- Выявление слабых категорий → доработка recognizer'ов.
