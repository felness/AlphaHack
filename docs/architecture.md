# Архитектура AlphaHack PII Security Module

## 1. Назначение

Сервис является защитным слоем между системой-потребителем и внешним обработчиком текста, например LLM. На прямом пути он обнаруживает и маскирует персональные данные, на обратном — восстанавливает исходные значения по сохранённой карте соответствий.

Реализация — Spring Boot-приложение, состояние корреляции вынесено в Redis. Для локального запуска доступно in-memory хранилище.

## 2. Контекст и поток данных

```text
┌────────────────────┐       ┌──────────────────────────────────────┐
│ Система-потребитель│──────▶│ RateLimitFilter                      │
└────────────────────┘       │   │                                  │
          ▲                  │   ▼                                  │
          │                  │ ProcessController                    │
          │                  │   │                                  │
          │                  │   ▼                                  │
          │                  │ ProcessService                       │
          │                  │   ├── SystemRegistry                 │
          │                  │   ├── DetectionEngine → Detector[*]  │
          │                  │   ├── MaskingEngine                  │
          │                  │   ├── UnmaskingEngine                │
          │                  │   ├── CorrelationStore               │
          │                  │   │     ├── Redis                    │
          │                  │   │     └── In-memory                │
          │                  │   └── MetricsService                 │
          │                  └──────────────────────────────────────┘
          └────────────────────────── JSON { result }
```

### 2.1. Маскирование

1. `RateLimitFilter` проверяет общий лимит экземпляра.
2. `ProcessController` валидирует JSON и передаёт запрос в `ProcessService`.
3. `SystemRegistry` выбирает конфигурацию по `X-System-Id` или использует `default`.
4. Хранилище ищет запись по `payload_id`.
5. Если записи нет, `DetectionEngine` запускает все Spring-компоненты `Detector`.
6. Результаты фильтруются по confidence, проверяются границы и разрешаются пересечения.
7. Разрешённые для системы типы передаются в `MaskingEngine`.
8. Исходный текст, маска, spans и система-владелец сохраняются в `CorrelationStore`.
9. Клиент получает `{ "result": "<маска>" }`.

### 2.2. Повтор и демаскирование

Если запись по `payload_id` уже существует:

- повтор исходного `payload` возвращает сохранённую маску без повторной детекции;
- другой `payload` считается обратным потоком и передаётся в `UnmaskingEngine`;
- точное совпадение с сохранённой маской возвращает исходный текст дословно;
- изменённый текст восстанавливается по сохранённым позициям, если spans остаются валидными;
- демаскирование разрешено только системе-владельцу и только при `unmasking-enabled: true`.

`payload_id` должен быть уникален для одной пары «исходный текст — маска». Клиенту не следует повторно использовать его для другого сообщения.

## 3. Контракт API

Единственная прикладная операция:

```http
POST /process
Content-Type: application/json
X-System-Id: <optional>

{
  "payload": "<непустая строка>",
  "payload_id": "<непустой идентификатор>"
}
```

Успешный ответ:

```json
{"result":"<обработанная строка>"}
```

| Код | Источник |
|---:|---|
| `200` | Успешная обработка |
| `400` | Bean Validation, неверный JSON или превышение `max-payload-size` |
| `403` | Неизвестная/отключённая система, запрет демаскирования или чужая запись |
| `429` | Bucket4j не выдал токен; ответ содержит `Retry-After` |
| `500` | Непредвиденная ошибка |
| `503` | Ошибка Redis или открытый circuit breaker |

## 4. Модель обнаружения ПД

### 4.1. Контракт детектора

Каждый детектор реализует интерфейс:

```kotlin
interface Detector {
    val supportedTypes: Set<PiiType>
    fun detect(text: String): List<DetectedEntity>
}
```

`DetectedEntity` содержит тип, полуоткрытый диапазон `[start, end)`, confidence, источник и признак checksum-валидации. Новый детектор автоматически попадает в `List<Detector>` через dependency injection.

### 4.2. Поддерживаемые категории

| Категория | Основной механизм |
|---|---|
| ФИО | шаблоны имени, отчества и контекстные правила |
| Дата рождения / дата выдачи паспорта | числовые и текстовые даты с классификацией по контексту |
| Место рождения | словарный шаблон и контекст |
| Паспорт РФ | регулярные выражения для вариантов серии и номера |
| Гражданство | словарные шаблоны |
| Орган выдачи паспорта | словарные шаблоны и контекст |
| Код подразделения | регулярное выражение и обязательный контекст |
| Водительское удостоверение | регулярное выражение и контекст |
| Адрес | составные адресные признаки, позитивный и негативный контекст |
| Email | регулярное выражение |
| Телефон | регулярное выражение |
| ИНН | регулярное выражение, контекст и checksum |
| Банковская карта | регулярное выражение, контекст и алгоритм Luhn |
| CVV / PIN | регулярные выражения с явными маркерами контекста |
| Имя держателя карты | латинское имя с контекстом карты |
| Загранпаспорт | дополнительный regex-детектор с контекстом |
| СНИЛС | дополнительный regex-детектор |

Всего в `PiiType` 19 значений: 17 обязательных категорий задания и 2 дополнительных.

### 4.3. Агрегация результатов

`DetectionEngine`:

1. объединяет ответы всех детекторов;
2. отбрасывает confidence ниже `0.7`;
3. удаляет spans с некорректными границами;
4. разрешает пересечения по приоритету типа, затем по confidence.

Для чувствительных коротких числовых значений (`CVV`, `PIN`) задан повышенный приоритет, далее идут карта, паспорт, ИНН, телефон, email, даты, ФИО и адрес. Это предотвращает двойное маскирование одного диапазона.

## 5. Маскирование и восстановление

`MaskingEngine` заменяет только буквы и цифры, сохраняя длину строки, пробелы и знаки-разделители.

| Формат | Поведение |
|---|---|
| `STAR` | Буквы и цифры заменяются на `*` |
| `TOKEN` | Буквы и цифры заменяются на `X` |
| `SYNTHETIC` | Цифры и буквы заменяются случайными символами соответствующего класса |

Маскирование применяется с конца строки, поэтому исходные позиции не сдвигаются. Для каждого диапазона сохраняется `MaskedSpan(type, start, end, original)`.

`UnmaskingEngine` также проходит spans с конца и подставляет сохранённые оригиналы. Надёжный round trip гарантирован для неизменённой маски. Если внешний обработчик изменил длину или расположение маски, восстановить затронутые spans корректно невозможно.

## 6. Хранилище корреляций

Интерфейс `CorrelationStore` имеет операции `save`, `find` и `delete`.

### Redis

- включён по умолчанию (`pii.store.type=redis`);
- ключ: `pii:corr:<payload_id>`;
- значение: JSON с исходным текстом, маской, spans, владельцем и временем создания;
- запись создаётся атомарно через `SETNX`;
- TTL по умолчанию — 86 400 секунд;
- вызовы защищены circuit breaker `redisStore`.

Исходные ПД хранятся в Redis до истечения TTL, поэтому Redis является частью доверенного контура: в production необходимы сетевое ограничение доступа, аутентификация и защита данных инфраструктурными средствами.

### In-memory

`ConcurrentHashMap` используется при `pii.store.type=in-memory`. Режим удобен для разработки и тестов, но данные теряются при рестарте и не разделяются между экземплярами приложения.

Автоматического переключения с Redis на in-memory при сбое нет: недоступность Redis приводит к `503`.

## 7. Конфигурация систем-потребителей

`pii.systems` содержит именованные профили:

```yaml
pii:
  systems:
    default:
      enabled: true
      masking-types: [ALL]
      unmasking-enabled: true
      mask-format: STAR
```

- неизвестная или отключённая система получает `403`;
- `masking-types` ограничивает набор маскируемых `PiiType`;
- `ALL` разрешает все найденные типы;
- запись содержит `systemId`, что исключает демаскирование другой системой;
- configuration properties помечены `@RefreshScope`, endpoint `/actuator/refresh` опубликован.

## 8. Производительность и отказоустойчивость

- Java 21 virtual threads включены через Spring Boot;
- Tomcat настроен на 10 000 соединений и очередь 1 000;
- rate limit по умолчанию — 2 000 RPS на экземпляр;
- таймаут подключения к Redis — 500 мс;
- circuit breaker открывается при 50% ошибок после минимум 5 вызовов и пробует восстановиться через 5 секунд;
- экземпляры приложения можно горизонтально масштабировать при общем Redis;
- локальный Bucket4j-лимит не координируется между экземплярами, поэтому суммарный лимит растёт вместе с их количеством.

`load_test.py` позволяет измерить фактические RPS и latency на целевом окружении. Числа производительности не фиксируются архитектурой и должны подтверждаться отдельным прогоном для конкретной инфраструктуры.

## 9. Безопасность и наблюдаемость

- `ProcessService` не пишет содержимое `payload` в логи;
- `payload_id` перед логированием преобразуется в безопасное представление;
- логируются типы сущностей и агрегаты, но не обнаруженные значения;
- API-ошибки скрывают внутренние детали;
- Micrometer публикует счётчики запросов, маскирования, демаскирования, ошибок и сущностей по типам;
- timers публикуют общую latency и latency обоих направлений с p50/p95/p99;
- Actuator публикует `health`, `info`, `prometheus`, `metrics` и `refresh`.

## 11. Проверка и ограничения

Тестовый набор покрывает детекторы, checksum, контекст, пересечения, маскирование/демаскирование, API, системный доступ, rate limiting, размер payload, безопасность логов и Redis-интеграцию. Redis-тесты запускаются через Testcontainers и пропускаются, если Docker недоступен.

Ключевые ограничения текущей реализации:

- детекция основана на правилах и словарях; ML/NER-модели нет;
- качество на новых доменах зависит от полноты шаблонов и контекста;
- изменение внешней системой длины или расположения маски нарушает позиционное восстановление;
- `payload_id` является глобальным ключом Redis, поэтому должен генерироваться уникально;
- Redis хранит оригинальные ПД и должен быть защищён как чувствительное хранилище;
- in-memory режим не подходит для нескольких экземпляров и долговременного хранения.
