## 0. Общие сведения и допущения

### 0.1. Контракт

```
POST /process
Content-Type: application/json

Запрос:  { "payload": "<строка>", "payload_id": "<идентификатор>" }
Ответ:   { "result": "<строка>" }
```

- **Первый запрос** с новым `payload_id` → **маскирование**.
- **Второй запрос** с тем же `payload_id` → **демаскирование** (восстановление исходной строки).
- Повторный запрос с тем же `payload_id` и тем же `payload` → **тот же результат** (идемпотентность).

### 0.2. Коды ответов

| Код | Ситуация |
|-----|----------|
| **200** | Успешная обработка |
| **400** | Некорректный запрос (нет `payload` / `payload_id`, пустой payload) |
| **403** | Неизвестная или отключённая система (`X-System-Id`) |
| **404** | Соответствие по `payload_id` не найдено (для демаскирования) |
| **429** | Too Many Requests (с `Retry-After`) |
| **500** | Внутренняя ошибка сервиса |
| **503** | Redis недоступен (деградация) |

### 0.3. Формат маски (текущая реализация `MaskingEngine.maskValue`)

- Каждый **буквенно-цифровой** символ (`isLetterOrDigit()`) заменяется на `*`.
- **Разделители сохраняются**: точка `.`, дефис `-`, пробел, слэш `/`, `@`, `+`, `(`, `)`, `_`, `%`.
- Длина маски **равна** длине оригинала.
- Служебные слова («серия», «ул.», «года», «номер») **не маскируются** (не входят в span).

### 0.4. Критичные допущения по текущему коду (важно для тестов)

> Эти пункты выявлены при анализе `src/main/kotlin/com/alfahack/pii/` и **должны быть учтены** при интерпретации ожидаемых результатов. Часть из них — известные пробелы реализации, которые тесты должны зафиксировать.

1. **Реализованы все 17 детекторов**: 11 regex (`EmailDetector`, `PhoneDetector`, `InnDetector`, `CardDetector`, `PassportDetector`, `DateDetector`, `CvvDetector`, `PinDetector`, `DepartmentCodeDetector`, `DriverLicenseDetector`, `CardHolderNameDetector`) + 5 словарных (`NameDetector`, `AddressDetector`, `CitizenshipDetector`, `PlaceOfBirthDetector`, `PassportIssuerDetector`). Все 17 категорий ПД покрыты.
2. **Порог уверенности** `DetectionEngine.DEFAULT_MIN_CONFIDENCE = 0.7`. Сущности с `confidence < 0.7` отбрасываются.
3. **Checksum-валидация** влияет на `confidence`:
   - ИНН: валидный → `0.95`, невалидный → `0.5` (отбрасывается).
   - Карта (Luhn): валидная → `0.95`, невалидная → `0.5` (отбрасывается).
   - Паспорт, телефон, email, дата: всегда `confidence ≥ 0.85` (без checksum-отбрасывания).
4. **Примеры из ТЗ могут не проходить checksum**:
   - `4276 1234 5678 9012` **не проходит Luhn** → в текущей реализации **не маскируется** (confidence 0.5). Для маскирования нужен Luhn-валидный номер, например `4276 1234 5678 9014`.
   - `770123456789` **не проходит контрольную сумму ИНН** → **не маскируется**. Валидный ИНН: `770100000079` (12 цифр), `7701000001` (10 цифр).
5. **Контекстные правила и словарные детекторы** (ФИО, адреса, гражданство, орган выдачи, код подразделения, в/у, CVV, PIN, имя держателя) **не реализованы** в текущем коде. Матрица контекстных правил (раздел 3) описывает **целевое поведение** и должна быть реализована вместе с детекторами.
6. **Регистронезависимость**: только `EmailDetector` использует `Pattern.CASE_INSENSITIVE`. Остальные regex-детекторы регистрозависимы (для цифровых типов это не критично, но для email важно).

### 0.5. Метрика качества

- Нормированное **span-based расстояние Левенштейна** [0..1], маска сравнивается с оригиналом.
- **Лишние маски штрафуются СЛАБЕЕ, чем пропуски** → стратегия «лучше перемаскировать».
- Цель: **средняя метрика ≥ 95%**.
- Разделители можно оставлять; длина маски не критична; служебные слова маскировать не нужно.

> - ✅ **Маскируется** — ожидается, что значение будет заменено на `*`.
> - ❌ **Не маскируется** — ожидается, что значение останется без изменений (ложное срабатывание / невалидный формат).
> - ⚠️ **Зависит от реализации** — текущий код не имеет детектора; поведение фиксируется как спецификация.
> - Маска приводится в формате текущего `MaskingEngine` (буквы/цифры → `*`, разделители сохраняются).

## 2. Матрица тест-кейсов демаскирования

> Демаскирование выполняется при повторном запросе с тем же `payload_id`. Восстановление идёт **по spans** (карте соответствий), сохранённой в Redis/in-memory при маскировании.

| UM-02 | `payload="email ivanov@mail.ru"`, `payload_id="p2"` → `"email ******@****.**"` | `payload="email ******@****.**"`, `payload_id="p2"` | `result="email ivanov@mail.ru"` |

| UM-04 | `payload="ИНН 770100000079"`, `payload_id="p4"` → `"ИНН ************"` | `payload="ИНН ************"`, `payload_id="p4"` | `result="ИНН 770100000079"` |

## 6. Параметризованные CSV-тесты

### 6.1. Формат CSV-файла

Колонки (разделитель `;`, кодировка UTF-8):

```
payload;payload_id;expected_mask;expected_unmask;category
```

| Колонка | Описание |
|---------|----------|
| `payload` | Входная строка (оригинал) |
| `payload_id` | Идентификатор корреляции |
| `expected_mask` | Ожидаемая маска (результат первого запроса) |
| `expected_unmask` | Ожидаемый оригинал (результат второго запроса) |
| `category` | Категория ПД (для отчёта) |

### 6.2. Как прогнать полную матрицу через CSV

1. **Параметризованный тест** (JUnit `@ParameterizedTest` + `@CsvFileSource`) читает CSV.
2. Для каждой строки:
   - Шаг 1: `POST /process` `{payload, payload_id}` → сравнить `result` с `expected_mask`.
   - Шаг 2: `POST /process` `{payload: expected_mask, payload_id}` → сравнить `result` с `expected_unmask`.
3. **Отчёт по категориям**: сгруппировать результаты по `category`, посчитать precision/recall/F1 и span-based Левенштейн.
4. **Цель**: средняя метрика ≥ 95%.

### 6.3. Пример CSV-файла (20+ строк, покрывающих все 17 категорий)

```csv
payload;payload_id;expected_mask;expected_unmask;category
паспорт 4509 123456;csv-01;паспорт **** ******;паспорт 4509 123456;PASSPORT_SERIES_NUMBER
серия 4509 номер 123456;csv-02;серия **** номер ******;серия 4509 номер 123456;PASSPORT_SERIES_NUMBER
```

## 7. Пограничные случаи

### 7.1. Пустой payload

| # | Вход | Ожидание |
|---|------|----------|
| ED-01 | `payload=""` (пустая строка) | **400** (валидация `@NotBlank`). |
| ED-02 | `payload` отсутствует в JSON | **400**. |
| ED-03 | `payload_id` отсутствует в JSON | **400**. |
| ED-04 | `payload="   "` (только пробелы) | **400** (`@NotBlank`). |
| ED-05 | `payload=" "` (один пробел) | **400**. |
| ED-06 | `payload` = `null` | **400**. |
| ED-07 | Некорректный JSON | **400** (`HttpMessageNotReadableException`). |

### 7.2. Очень длинный текст (до 100 000 токенов)

| # | Вход | Ожидание |
|---|------|----------|
| ED-08 | Текст ~100 000 токенов с ПД в начале, середине и конце | Все ПД маскируются; latency ≤ 1 сек. |
| ED-09 | Текст ~100 000 токенов без ПД | Ничего не маскируется; быстрая обработка (regex-скрининг). |
| ED-10 | Текст > `max-payload-size` (1 000 000 символов) | **400** (защита от DoS). |
| ED-11 | ПД на границе чанка (при чанкинге) | ПД корректно детектируется (перекрытие границ). |

### 7.3. Спецсимволы, Unicode, эмодзи

| # | Вход | Ожидание |
|---|------|----------|
| ED-12 | `ivanov@mail.ru` с эмодзи рядом: `😀 ivanov@mail.ru` | Маскируется только email, эмодзи не трогается. |
| ED-13 | `+7 (900) 123-45-67` с Unicode-пробелами | Зависит от regex; целевое поведение — маскируется. |
| ED-14 | `паспорт 4509 123456` с табуляцией `4509\t123456` | Зависит от regex (`[\s\-]?` — табуляция не входит в `\s`? — `\s` включает табуляцию). |
| ED-15 | Email с `+` в имени: `ivanov+test@mail.ru` | ✅ Маскируется → `******+****@****.**` (`+` сохраняется). |
| ED-16 | Email с `%` в имени: `ivanov%test@mail.ru` | ✅ Маскируется → `******%****@****.**` (`%` сохраняется). |
| ED-17 | Кириллица в email-домене: `ivanov@почта.рф` | Зависит от regex (ASCII-only); целевое поведение — маскируется. |
| ED-18 | Спецсимволы внутри номера карты: `4276-1234-5678-9014` | ✅ Маскируется → `****-****-****-****`. |

### 7.4. Пересекающиеся spans

| # | Вход | Ожидание |
|---|------|----------|
| ED-19 | `12.05.1990` (дата) внутри текста с телефоном | Разрешение пересечений: выбирается более специфичный тип. |
| ED-20 | `4509 123456` (паспорт) и `12.05.1990` (дата) рядом | Оба маскируются, без перекрытия. |
| ED-21 | Номер карты `4276 1234 5678 9014` и CVV `123` рядом | Приоритет: `CARD_NUMBER` (80) > `CVV` (100) — CVV специфичнее. |
| ED-22 | `770100000079` (ИНН) внутри `770100000079` (12 цифр) | Маскируется как ИНН (приоритет 60). |
| ED-23 | Перекрытие `FULL_NAME` и `ADDRESS` | Приоритет: `ADDRESS` (10) < `FULL_NAME` (20) — FULL_NAME специфичнее. |

### 7.5. Регистронезависимость

| # | Вход | Ожидание |
|---|------|----------|
| ED-24 | `IVANOV@MAIL.RU` | ✅ Маскируется (email — `CASE_INSENSITIVE`). |
| ED-25 | `Паспорт 4509 123456` (заглавная «П») | ✅ Маскируется (цифры регистронезависимы). |
| ED-26 | `ИНН 770100000079` / `инн 770100000079` | ✅ Маскируется (цифры). |
| ED-27 | `IVANOV IVAN` (имя держателя, заглавные) | ⚠️ Маскируется (целевое поведение, регистронезависимость). |

### 7.6. Безопасность (отсутствие утечек ПД)

| # | Сценарий | Ожидание |
|---|----------|----------|
| SEC-01 | Логирование при маскировании | В логах **нет** значений ПД (только типы: `FULL_NAME, PASSPORT_SERIES_NUMBER`). |
| SEC-02 | Логирование при демаскировании | В логах **нет** `original`, `mask`, `spans` (значений). |
| SEC-03 | Метрики Prometheus | Нет тегов/значений ПД; только агрегаты (latency, RPS, количество). |
| SEC-04 | Ошибка 500 | Сообщение об ошибке не содержит ПД (`Internal server error`). |
| SEC-05 | `payload_id` в логах | Логируется хеш, не сам `payload_id` (если он содержит ПД). |
| SEC-06 | Данные в Redis | `original`, `mask`, `spans` могут быть зашифрованы (AES) — опционально. |

### 7.7. Производительность

| # | Сценарий | Ожидание |
|---|----------|----------|
| PERF-01 | Нагрузка 1000 RPS | Latency p95 < 1 сек. |
| PERF-02 | Нагрузка 2000 RPS (цель) | Latency p95 < 1 сек. |
| PERF-03 | 200 параллельных коннектов | Нет деградации, нет 429 (при лимите 2000 RPS). |
| PERF-04 | Превышение rate limit | **429** с `Retry-After`. |
| PERF-05 | Большой текст (100 000 токенов) | Обработка ≤ 1 сек (линейная сложность). |

### 8.2. Критичные пробелы, требующие реализации (для достижения ≥ 95%)

1. **Параметризованное покрытие всех 17 категорий** — CSV расширен до всех категорий (см. `masking-cases.csv`), но точность масок для словарных/контекстных детекторов требует настройки.
2. **Контекстные правила** — реализованы (`ContextRules`), но требуют тонкой настройки порогов и словарей.
3. **Разделение `DATE_OF_BIRTH` / `PASSPORT_ISSUE_DATE`** — реализовано по контексту (`DateDetector.resolveType`).
4. **Регистронезависимость** — реализована для email и контекстных детекторов (`UNICODE_CHARACTER_CLASS`).
5. **Примеры из ТЗ** (`4276 1234 5678 9012`, `770123456789`) не проходят checksum — в тестах используются Luhn/checksum-валидные аналоги.
